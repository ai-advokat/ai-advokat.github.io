# OIC2 — atomic source gate
Date: 2026-11-25. Original design baseline: 6cf8d9ea2410e9165973f4e315dafb87c49c741f.
Status: LOCAL IMPLEMENTATION CANDIDATE for document snapshots and revisions, based on `700c5ad`. HUMAN GATE HOLD; LEGAL_HOLD ACTIVE; PRODUCTION NO-GO.
No deployment, migration, provider activation, or release authorized.

## Observed gap
The existing response review is a historical receipt: appendResponseReview performs a single conditional D1 INSERT for the decision sequence and current actor/key/entitlement/role. handleResponseRevisionReview reads the revision, immutable draft receipt and current extraction bytes before that INSERT. These observations are not one atomic transaction across D1 and R2. A change between the final read and INSERT is possible. A case fingerprint is not an authority epoch or a proof of current law. R2 conditional creation of a revision does not make the D1 source snapshot atomic. Never treat a receipt as a release token; no approval can override active LEGAL_HOLD. Existing general non-response professional export also accepts client report sections; keep that risk in scope for the release gate.

## Proposed architecture (one existing Worker, one authorization system)
1. Establish one authoritative D1 integrity state for each case/draft, with monotonic revision/head, source, authority, authorization and hold epochs; default deny if missing. All effective document/extraction/analysis/authority/access/hold mutation paths must advance the appropriate epoch in the same authoritative transaction, including deletion, re-extraction, replacement, role/key/entitlement revocation and rollback/restore. A global authority change must also be captured by a governed authority epoch; do not equate a stored citation with current law.
2. For R2, stage immutable content-addressed object bytes privately, verify SHA-256 from actual bytes, and publish the pointer and epoch through a conditional D1 transaction. For D1 fallback, equivalent immutable object identity and pointer commit are required. Mutable legacy object keys must not remain an authoritative release path. R2 and D1 do not provide a single cross-service ACID transaction: the D1 pointer commit is the linearization point; orphan staged objects are never release evidence. No overwrite/restore of published bytes is permitted; digest mismatch or missing storage blocks release.
3. Bind explicit review to actor, decision sequence, exact immutable revision/draft identity, source snapshot, authority snapshot and all captured epochs. Use a conditional D1 write whose predicate checks the expected state and membership at write; zero changed rows is a conflict, not success. Revocation advances the decision/hold state; a later return to identical text/bytes cannot revive an old approval. Preserve historical receipts, not current authorization.
4. Professional export remains disabled. For future reviewed implementation, reserve an export only for the exact approved revision and trusted canonical server model; render privately, hash output, then perform a final conditional D1 commit/recheck of current head, snapshots, epochs, active authorization, current decision and hold state before releasing bytes. Persist receipt with model/artifact hashes and renderer version. No client report, actor identity, approval flag or browser-generated PDF is trusted for professional release. A fresh request must always recheck, including retries; define revocation linearization relative to already-authorized in-flight delivery. No filing/signing/transmission.
5. Treat storage/DB/authority validation failure as locked. Keep working exports visibly unapproved. Review retention, deletion, access privacy and recovery of orphan objects, with synthetic inputs only. Migrations, if required, must be explicitly reviewed and exercised in a disposable local/isolated database; do not apply the frozen migrations or this design to remote resources.

## Local document and revision candidate

- Existing Worker routes exercise the candidate when the local fixture sets `CASE_ATOMIC_RESPONSE_ENABLED=true` and applies [the proposed schema](PROPOSED_ATOMIC_RESPONSE_STATE.sql) to a disposable database. For a repeatable local run, use `node --no-warnings --test test/case-response-atomic-state.test.mjs`. The proposal lives outside the migration directory. A configured Worker without the schema fails closed on atomic revision writes. A case with preexisting legacy revision objects needs a separate cutover before its first atomic revision can be written.
- Source edits run through document-slot mutations (upload reservation and commit, multipart quarantine and abort, deletion) or through an extraction publication. Slots and extraction publications advance the same D1 counter. A repeated extraction advances the counter even when the object digest matches. D1 commits the extraction pointer, counter, slot status and audit together. The existing private storage adapter stages an immutable object and checks its SHA-256 before publishing. Analysis and draft provenance carry the captured source epoch.
- Revision objects stage under their byte digest. D1 publishes only if the expected parent number and hash, source epoch and current write access still match. History and exact reads use the D1 publications in this mode. Review uses one conditional D1 audit insert to check the latest revision, epoch, decision predecessor and current writer. Revocation can still target the last historical decision after the source changed. Published objects must pass byte hash checks when read.
- The authorization proposal tracks account eligibility, keys, the selected entitlement, workspace status and actor-specific case grants. SQLite triggers record mutations in the same transaction and preserve epochs across reinsertions of the same identity. Publication and decision predicates compare the captured epochs and expiry at write time. A prior receipt is stale if access changed or the original credential or selected entitlement expired. A grant change for a different case does not invalidate this case's receipt.
- The local legal-source proposal tracks mutations to the shared D1 corpus used by response analysis, including official-source and statutory version tables, Gazette records, and judgment authority, verified binding and publication gates. Those mutations age all snapshots conservatively. A private CasePilot classification ages only the affected case. Analysis captures both epochs before retrieval, the immutable draft receipt binds them to its digest, and the revision and review writes compare them in their conditional D1 statements. Returning a record to its old values cannot revive the old epoch.
- The Worker embeds a generated SHA-256 of runtime sources under `src`, including the static legal rules. This first version conservatively includes all source modules. Regenerate with `node scripts/case-response-worker-policy.mjs --write` after Worker source changes. `npm run verify` detects a stale generated value. The separately reviewed D1 policy row binds the approved digest to the environment, and the Worker compares both its compiled digest and the D1 registry epoch. Registering, removing or changing the digest advances the epoch, including a return to an earlier digest.
- The Worker captures the D1 clock together with the applicable Skopje civil date, then expires evidence at the next civil midnight. Atomic analysis uses that date when the question supplies no explicit ISO reference date. The same D1 predicates compare the captured interval when deciding or publishing. Midnight requires fresh analysis even when the instrument version and D1 data are identical. This conservative daily window covers date-level transitions and both daylight-saving changes.
- The isolated export validation records two server-computed digests and the exact approved decision and revision. Its conditional D1 audit insert rechecks the latest head and decision, evidence and legal-source epochs, time window, current writer and captured reviewer authorization, and validation hold epoch after rendering. The HTTP delivery check accepts working models with pending status. The validation policy defaults to HOLD and only produces synthetic audit evidence when exercised in a disposable database.
- Remaining scope includes legal policy inputs outside the Worker sources, canonical production rendering including server-side PDF, integration of any actual professional delivery under a separate release authorization, remote binding and HTTPS verification, and retention/reconciliation for immutable historical and unreferenced staged objects. Document deletion marks the slot in D1 before raw storage cleanup in this mode. Immutable derived artifacts require an explicit retention policy before any use with real data.
